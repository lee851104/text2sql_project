# 資料血緣清單

這五份 CSV 回答同一個問題：**這個專案的資料是怎麼來的。**

從八份台電官方開放資料，經過清洗與對齊，變成資料庫裡的 18 張表與 6 個語意檢視。
每個環節都可以在這裡查到來源、規則與實測數字。

用試算表軟體開啟即可（UTF-8 with BOM，Excel 不會亂碼）。

## 五份檔案

| 檔案 | 列數 | 回答什麼 |
|---|---:|---|
| [01_資料來源.csv](01_資料來源.csv) | 8 | 每份原始資料來自哪個官方資料集、什麼時候更新、多大、放在哪 |
| [02_清洗規則.csv](02_清洗規則.csv) | 34 | 每份資料做了什麼處理、程式寫在哪個檔案的哪個函式、實測效果是什麼 |
| [03_對齊產物.csv](03_對齊產物.csv) | 22 | `taipower_align/` 每個檔案是來源副本、程式衍生還是人工維護 |
| [04_資料表與檢視.csv](04_資料表與檢視.csv) | 24 | 資料庫每張表與檢視的列數、資料從哪來、Text2SQL 能不能查 |
| [05_陷阱與人工裁決.csv](05_陷阱與人工裁決.csv) | 22 | 踩過的坑、需要人判斷的決定、目前還做不到的事 |

## 怎麼讀

**想知道某個數字從哪來** → 先查 `04`，找到那個檢視的「資料來自」，再到 `01` 查那份原始資料的官方出處。

**想知道某份資料被動了什麼手腳** → `02` 用「來源檔」欄篩選，每條規則都標了實作位置，可以直接翻程式碼對照。

**想知道哪些數字不能直接用** → `05` 的「資料陷阱」類別。這些是實際踩到的，不是理論上的風險。

## 幾個原則

這個專案處理資料時遵守三條規則，看 CSV 時會一直遇到：

1. **原始檔不修改。** 官方原檔逐字保存，清洗全部發生在讀取期。`03` 裡標「來源副本」的八個檔與 `data/raw/` 位元組相同。
2. **程式不猜測。** 無法用規則確定的對應，一律寫進 `configs/` 的設定檔並附判斷依據，不在程式裡硬編。`05` 的「人工裁決」類別列出目前所有這類決定。
3. **缺值與零要分開。** 官方標記無資料的存 NULL，不改寫成 0。「沒有資料」和「數值是零」在語意上是兩件事。

## 重現方式

```bash
uv run python -m ingest.fetch      # 下載八份原始資料並以 SHA-256 封存
uv run python -m align             # 產生對齊結果與報告
uv run python -m ingest.build_db   # 建立 SQLite 語意層
```

這五份 CSV 的數字都是從上述流程的實際產物量出來的，不是人工填的。

## 已知的不完整

- 火力與核能**沒有任何發電量資料**。目前只有 `v_re_generation` 有電量，而且僅限台電自建的再生能源場站（約全國風光地熱的 3～4%）。
- `v_peak` 有 3 個欄位仍無裝置容量（麥寮 #1／#2／#3）。
- 詳細情形與補救方向見 [資料擴充計畫](../DATA_ROADMAP.md)。
